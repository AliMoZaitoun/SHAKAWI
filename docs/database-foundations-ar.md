# دليل قاعدة البيانات والتطوير المحلي

## النتيجة وحدود المرحلة

هذه مرحلة باك إند، بدون تحويل الواجهة إلى React. بقيت SQLite ونظام الجلسات والبوت كما هي. لا تُحذف البيانات أو الأعمدة أو الملفات القديمة تلقائياً.

أصبح `users` المصدر الأساسي للاسم والهاتف واسم الدخول وكلمة المرور. خصائص المواطن والموظف تقرأ منه، وكتابات API القديمة تمرر التعديل إليه. بقيت أعمدة قديمة كمرايا توافق، لا كمصدر مستقل. أسماء الموظفين القديمة لا تُقسّم تخميناً، ولا تُخترع أرقام هاتف؛ الحساب الناقص معلّم للاستكمال. إزالة المرايا وفرض NOT NULL على البيانات الناقصة يحتاج موافقة وترحيلاً لاحقاً، لا حذف قاعدة البيانات.

## خريطة الجداول

```text
users ── citizens ── complaints ── complaint_history
  └──── employees ── employee_role_assignments ── roles ── role_permissions ── permissions
                              └── directorates

languages ── role_translations ── roles
          ├─ permission_translations ── permissions
          ├─ directorate_translations ── directorates
          └─ user_languages ── users

files ── complaint_files ── complaints
      ├─ citizen_files ── citizens
      └─ evidence_reply_files ── evidence_replies

audit_events ── users (الفاعل اختياري للعمليات النظامية/المستوردة)
```

الملفات نفسها في `uploads/` وليست BLOB داخل قاعدة البيانات. لا توجد علاقة morph جديدة للملفات؛ جداول الربط تفرض Foreign Keys. بقيت سجلات attachments وevidence_files القديمة للحفاظ على معرفات وروابط التنزيل القديمة، وتُزامن مع الكتالوج في المعاملة نفسها. لا تحذفها يدوياً.

`complaint_history` سجل أعمال خاص بالشكوى، و`audit_events` سجل تدقيق للنظام. الملاحظات وطلب الأدلة ليست بديلاً عن أي منهما. لا تعني نسبة الإنجاز تاريخاً حقيقياً لانتقالات لم نسجلها.

## اللغات

- يوجد جدول لغات؛ إضافة الفرنسية أو غيرها عملية بيانات وليس إضافة أعمدة.
- اسم الحقل داخل جداول الترجمات هو `name`، والوصف `description`، وللمديرية عنوان نصي مترجم `location`.
- لكل سجل ترجمة واحدة لكل لغة، بمفتاح مركب وروابط فعلية.
- الأولوية: `?lang=fr`، ثم تفضيل حساب المستخدم الموثوق، ثم `Accept-Language` حسب الجودة، ثم العربية. المطابقة الإقليمية ترجع إلى اللغة الأساسية إن كانت مفعلة.
- عند غياب ترجمة السجل: العربية، ثم أول ترجمة مفعلة متاحة، ثم اسم التوافق القديم. لا تترجم نصوص المواطن آلياً.
- ترويسة Content-Language تصف اللغة المطلوبة التي اختارها النظام؛ يمكن أن تستخدم بعض السجلات لغة الرجوع عند نقص ترجمتها.
- العربية لغة رجوع محمية من التعطيل ومن حذف ترجمتها الأساسية. لتعطيل لغة أخرى استعمل تعديل اللغة؛ لا نحذف مراجع ترجمتها.
- ترجمات الأسماء الإنجليزية المدمجة متاحة للأدوار والصلاحيات والمديريتين الافتراضيتين، ولا تُستبدل ترجمة موجودة بتشغيل جديد. تهيئة الترجمات الافتراضية المفقودة تعيد إنشائها؛ استخدم التعطيل إذا أردت منع عرض لغة.
- رموز مثل governor وcomplaints.view ثابتة، ولا تنشئ أدواراً منفصلة لكل لغة.
- هذا لا يجعل نصوص أزرار الموقع ورسائل البوت مترجمة تلقائياً إلى كل لغة جديدة. موارد رسائل البوت الحالية عربية وإنجليزية؛ قائمة المديريات في البوت تأتي من API مترجمة وبدون حصرها بمديريتين.

### مسارات اللغات

كل المسارات أدناه تبدأ بـ `/api/v1`:

| العملية | المسار | الوصول |
|---|---|---|
| اللغات المفعلة | GET /languages | عام |
| قائمة الإدارة | GET /admin/languages | rbac.manage عام |
| إضافة لغة | POST /admin/languages | rbac.manage عام |
| تعديل/تعطيل | PUT /admin/languages/{code} | rbac.manage عام |
| ترجمات سجل | GET /admin/translations/{entity}/{id} | rbac.manage عام |
| حفظ ترجمة | PUT /admin/translations/{entity}/{id}/{language} | rbac.manage عام |
| حذف ترجمة غير العربية | DELETE /admin/translations/{entity}/{id}/{language} | rbac.manage عام |
| تفضيل المستخدم | PUT /language-preference | جلسة موظف سارية أو ملكية مواطن موثوقة |

entity أحد roles أو permissions أو directorates. معرف permission هو الرمز، وليس رقماً.

مثال إضافة لغة:

```json
{"code":"fr","name":"Français","direction":"ltr","is_active":true}
```

مثال ترجمة مديرية:

```json
{"name":"Services municipaux","description":"Description","location":"Centre"}
```

تظل حقول name/description/location في APIs الإدارية القديمة متوافقة، وتكتب النسخة العربية. لإدخال لغة أخرى استخدم API الترجمات، وليس الاسم العربي القديم.

## الملفات

- الكتالوج يخزن storage_disk وstorage_key الداخلي والاسم الأصلي المنظف وMIME والحجم وSHA-256 ورافع الملف إن كان معلوماً.
- ملفات قديمة بلا بايتات متاحة تُحفظ مراجعها مع حجم وبصمة فارغين؛ التنزيل يعيد 404، وليس نجاحاً وهمياً. لا تُنشأ ملفات بديلة.
- مسار التنزيل الموحد: `GET /api/v1/files/{id}/download`.
- الوصول مرتبط بالشكوى/طلب الأدلة/المواطن، وليس بمعرفة file_id.
- رمز تتبع شكوى يعطي الوصول لملفات تلك الشكوى المسموحة فقط، ولا يعطي صور الهوية أو سجل المواطن كله.
- قراءة هوية مواطن متاحة لصاحب الحساب الموثوق أو موظف بصلاحية files.identity.read ضمن نطاق عام؛ ليس لكل موظف تلقائياً.
- صورة الهوية تظل خاصة حتى لو نُشرت الشكوى. الملفات المرتبطة بهوية لا تتجاوز حمايتها عبر رابط شكوى قديم.
- الرفع بحد 10MiB لكل ملف، وطلب الأدلة بحد خمسة ملفات. الصور وPDF تُفحص فعلياً؛ يُرفض النوع المزور وPDF النشط أو المشفر. ملفات الصوت والفيديو المدعومة تفحص توقيع الحاوية، وليس فحص برمجيات خبيثة شاملاً.
- لا توجد خدمة مكافحة فيروسات أو object storage في هذه المرحلة؛ لا تدّع خلاف ذلك في التسليم.
- فشل حفظ قاعدة البيانات يحذف بايتات الرفع الجديد فقط. استبدال الهوية لا يحذف القديمة دون سياسة احتفاظ معتمدة.
- بعد توقف مفاجئ يمكن فحص الملفات اليتيمة بأمر القراءة فقط:

```bash
python -m dotenv -f .env run -- python -m scripts.inspect_storage
```

الأمر يعرض أعداداً فقط، ولا يحذف ملفات أو يطبع هويات/مسارات. قرار الحذف والاحتفاظ يحتاج موافقة.

## التدقيق وتاريخ الشكوى

`audit_events` يحفظ الحدث والهدف والتغييرات المسموحة والفاعل والمصدر ومعرف طلب يولده الخادم. المصدر web أو telegram الموثّق أو system أو migration. العمليات التي تتم قبل إثبات الحساب قد تسجل دون فاعل؛ لا نخمن هوية الفاعل.

- يشمل تغييرات الشكاوى والملاحظات وطلبات الأدلة والردود والمراجعة والأدوار وإسناداتها والملفات وبيانات المستخدم الحساسة كإشارات تغيير فقط، دون قيمها.
- يسجل تعديل كلمة المرور كعلامة فقط، لا كلمة المرور ولا hash. لا يسجل مفاتيح الاستعادة أو نصوص الأدلة أو أرقام الهوية أو صورها. تغيير صلاحيات الدور يسجل رموز الصلاحيات قبل وبعد.
- السجل والتعديل ضمن نفس معاملة SQL؛ rollback يلغي كليهما.
- لا يوجد API لتعديل/حذف سجل التدقيق، وكتابات ORM ترفض تعديل أحداث التدقيق والتاريخ. هذه ليست حماية من مدير قاعدة بيانات قادر على تجاوز التطبيق.
- رفض الدخول أو الصلاحية والحد من المحاولات يسجل في logger أمني منفصل بمعرف طلب وحالة، دون نص الطلب أو رمز التتبع أو عنوان IP؛ لا يضيع مع rollback معاملة الأعمال.
- القراءة المقسمة للصفحات: GET /api/v1/admin/audit-events بصلاحية audit.view عامة. يمكن الفلترة بـaction وentity_type.
- سجل access_audit القديم باقٍ، ويستورد إلى التدقيق المركزي كأحداث migration، دون ادعاء معرفة مصدرها الأصلي.

تاريخ الشكوى:

```text
GET  /api/v1/complaints/{id}/history
POST /api/v1/complaints/{id}/transfer
```

القراءة للموظف المخول أو مالك الشكوى/رمز تتبعها الموثوق. لا تُعرض للمواطن أسماء الفاعلين أو السبب الداخلي أو معرف الطلب.

التحويل يتطلب complaints.transfer في المديريتين، ومديرية هدف مفعلة، وسبباً. تعديل الحالة يقبل reason اختيارياً ويجمع تغيير الحالة والمديرية والإنجاز في حدث واحد لكل flush. سجلات ما قبل الترحيل تُعلّم imported_snapshot بتاريخ استيرادها؛ ليست تاريخاً قديماً مصطنعاً.

الصلاحيات الثلاث الجديدة audit.view وfiles.identity.read وcomplaints.transfer لا تُمنح آلياً للأدوار الموجودة عند إعادة التشغيل. على المدير منح المطلوب صراحة من API إدارة الأدوار. الأدوار الجديدة المدمجة لا تستنتج توزيعاً وظيفياً لم توافق عليه.

## الترحيلات والنسخ الاحتياطي

نقطة الترحيل الآن Alembic، ولا تُشغّل create_all كبديل عن migrations على قاعدة موجودة.

```bash
python -m dotenv -f .env run -- python -m app.db.upgrade
```

التطبيق يشغّل الترقية نفسها عند بدء التشغيل. تتبنى النسخة القديمة وتضيف الجداول الجديدة دون stamp أعمى. مسارات SQL الأولية مجمدة في migrations/، وأي تعديل مستقبلي بمراجعة جديدة. لا تعدّل تاريخ migrations بعد توزيعه.

- أول ترقية لقاعدة موجودة تنسخ SQLite وuploads إلى generated-artifacts/backups/ بصلاحيات محلية خاصة، وتنتج manifest وبصمات. النسخ لا تدخل ZIP أو Git.
- أوقف الموقع والبوت وكل كاتب آخر قبل الترقية أو النسخ اليدوي، لضمان اتساق قاعدة البيانات والبايتات. ترحيل بدء التشغيل يكون قبل استقبال الطلبات، لكن لا يستطيع منع كاتب خارجي تركته يعمل.
- تُقارن أعداد السجلات المحفوظة ويُفحص foreign_key_check. فشل الترحيل يتراجع عن DDL والبيانات داخل معاملة SQLite صريحة.
- العناوين القديمة غير المعروفة لملكية مرفق توقف الترحيل للمراجعة، لا تُهمل. اختلافات بيانات قديمة تمنع القيود تُبلّغ، ولا تُحذف سجلات لحلها.
- المفاتيح الفعلية موجودة للجداول الجديدة ولقاعدة جديدة. لا نعيد بناء الجداول القديمة لفرض جميع القيود الناقصة دون موافقة.
- لا توجد downgrade مدمرة آلية. الرجوع باستعادة النسخة المتحقق منها مع بايتات الملفات، وبنسخة الكود الموافقة لها.
- هذه المراجعات تستهدف SQLite القائمة. نقلها لمحرك آخر يحتاج ترحيلاً منفصلاً معتمداً، ولا يغيّر المشروع إلى قاعدة أخرى تلقائياً.

نسخة يدوية بعد إيقاف الكتّاب:

```bash
python -m dotenv -f .env run -- python -m app.db.backup create --writers-stopped
```

استعادة إلى مجلد جديد، دون استبدال المشروع أو قاعدة حية:

```bash
python -m app.db.backup restore generated-artifacts/backups/BACKUP_DIRECTORY restored-copy
```

بعدها تحقّق من النسخة المستعادة واستخدم الكود الموافق ووجّه التشغيل إلى قاعدتها وuploads الخاصة بها. لا تنسخ قاعدة قديمة فوق عملية تعمل. لا ترسل النسخ الاحتياطية أو ملفات المواطنين إلى GitHub.

## أين أعدّل؟ مقارنة مع Laravel

| Laravel | هنا |
|---|---|
| Eloquent Models | app/models/ |
| Form Requests / Resources | app/schemas/ وعقود الرد |
| Routes / Controllers | app/api/v1/endpoints/ وتسجيلها في app/main.py |
| Services | app/services/ |
| Migrations | migrations/versions/ عبر Alembic |
| Middleware | app/core/security.py وapp/services/foundation_middleware.py |
| Spatie Permission | app/services/access.py والجداول العلائقية |
| Activitylog | app/services/audit.py وaudit_events |
| Bot commands | bot/handlers/، states، keyboards |

لجدول جديد: عرّف الموديل واستورده ضمن metadata، أضف Schema وخدمة ومساراً محمياً حسب الحاجة، وأنشئ مراجعة Alembic وراجع SQL واختبرها على قاعدة فارغة وقديمة. لا تعتمد على إنشاء جدول عند الاستيراد أو الكتابة مباشرة في مرايا الهوية.

```bash
python -m dotenv -f .env run -- python -m alembic revision --autogenerate -m "describe_change"
```

راجع الملف الناتج: لا توافق على DROP أو إعادة بناء لمجرد أن autogenerate اقترحها. أضف اختبار صلاحيات ومهاجرة قبل التوزيع.
